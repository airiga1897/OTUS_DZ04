# Архитектура ДЗ04

База знаний о домашних заданиях OTUS реализована на Django + uWSGI и PostgreSQL.
Инфраструктура описана в Terraform, настройка серверов — в Ansible.

## Обоснование решения

Django предоставляет модель статей, административный интерфейс и миграции БД,
поэтому приложение позволяет проверить полноценный backend с PostgreSQL.
uWSGI выполняет требование задания к серверу приложения и обслуживает статику
из общего каталога без дополнительного HTTP-сервиса на backend.

Два фронта и два backend обеспечивают резервирование обслуживающих узлов.
Octavia распределяет соединения между фронтами, а Nginx — запросы между
приложениями. PostgreSQL оставлен некластеризованным по условию задания.

GFS2 размещена непосредственно на backend. DRBD выбран для учебного
исследования репликации их отдельных дисков без дополнительных ВМ хранения.
Ограничения этого сочетания и промышленная альтернатива описаны ниже.
Внешний qnetd на ВМ БД обеспечивает арбитраж для двухузлового кластера;
fencing используется для выключения узла в проверяемом сценарии разделения сети.

## Выбор облака и Terraform-провайдера

Для Yandex Cloud был направлен запрос на увеличение квот, необходимых
для пяти ВМ. С момента подачи запроса и на момент выполнения работы
предоставлено увеличение дисковых квот, но запрошенное увеличение квот
vCPU не предоставлено. Поэтому развёртывание выполнено в Selectel.

В конфигурации используется `terraform-provider-openstack/openstack`
версии 3.4.0. ВМ, диски, сети, группы безопасности и Octavia управляются
через OpenStack API Selectel. Использование этого провайдера предусмотрено
[документацией Selectel](https://docs.selectel.ru/terraform/providers/).

Проект и сервисные пользователи создаются отдельно в панели.
Их автоматическое создание не входит в Terraform-конфигурацию стенда,
поэтому подключение дополнительного провайдера `selectel/selectel`
не требуется. Выбранный подход позволяет управлять необходимыми ресурсами
одним провайдером, а параметры проекта передавать через локальные tfvars
и окружение без credentials в исходниках.

## Состав стенда

Конфигурация предусматривает пять ВМ в Selectel:

- nginx1 и nginx2 — два фронта Nginx за Selectel Octavia HA.
- backend1 и backend2 — Django + uWSGI, DRBD и GFS2.
- db — PostgreSQL и внешний арбитр Corosync qnetd.

Каждый фронт балансирует запросы между обоими backend по протоколу uwsgi.
Статика и загруженные изображения хранятся на GFS2 на backend:
uWSGI обслуживает `/static` и `/media` через static-map. Дополнительных HTTP-сервисов
на backend нет. Код приложения и venv находятся на локальных дисках;
collectstatic выполняется одним узлом в общий каталог.

## Общее хранилище

Для репликации дисков backend выбран DRBD с protocol C и dual-primary.
Поверх реплицируемого устройства настроена GFS2 с двумя журналами и DLM.
Порядок запуска ресурсов в Pacemaker: DRBD promoted → DLM → GFS2 → uWSGI.
Арбитр на db участвует в кворуме, но не хранит третью реплику данных.

DRBD dual-primary + GFS2 используется как учебный эксперимент. Постоянный
режим dual-primary в DRBD 9 не поддерживается и не тестируется LINBIT.
Наличие параметра allow-two-primaries не означает промышленной поддержки.
Даже успешные отказные испытания не отменяют этого ограничения.

Fencing реализован агентом, который вызывает выключение ВМ через Selectel Nova API.
Он разрешает выключение только двух backend-серверов, проверяя их
идентификаторы. Если указан другой сервер, агент отказывается его выключать.
Права сервисного пользователя с ролью compute.server.user распространяются
на проект целиком; ограничение двумя backend проверяется внутри агента,
а не правами доступа облака. Credentials оператора на backend не передаются.
Агент подтверждает выключение по состояниям SHUTOFF и power_state=4.
Проверки Stop на пустом стенде и выбранное разделение сети прошли;
это не является доказательством изоляции при всех отказах гостя и хранилища.

В конфигурации запрещены запуск uWSGI без монтирования общего каталога,
локальная запись приложения в незамонтированный каталог и доступ uWSGI
к metadata. Readiness проверяет mount, маркер GFS2 и запрос к PostgreSQL.

## Границы отказоустойчивости

Предусмотрена балансировка на уровне фронтов и приложений. PostgreSQL
развёрнут в единственном экземпляре по условию задания: отказ БД приводит к недоступности
динамических страниц. Все пять ВМ находятся в одной зоне, поэтому отказ зоны
эта архитектура не покрывает. Репликация не заменяет резервное копирование.

## Рекомендация для промышленной эксплуатации

Для промышленной эксплуатации рекомендуется отказоустойчивое общее блочное
хранилище с резервируемыми iSCSI-контроллерами и несколькими путями доступа.
Оба backend подключают один согласованный LUN через multipath и используют GFS2.

Возможная реализация — два выделенных storage-узла с DRBD single-primary
и переключением iSCSI target в режиме active-passive. При переключении
должны сохраняться данные и идентичность LUN/WWID. Резервирование контроллеров
защищает от отказа узла хранения, multipath — от отказа пути доступа.
Два портала одной ВМ не обеспечивают резервирование контроллеров;
два независимых диска нельзя объединять multipath как один LUN.

Такая схема требует отдельного проектирования адресации, переключения
подключений, fencing и восстановления путей, а также дополнительных
storage-узлов. Она не входит в учебный стенд из пяти ВМ.

## Проверка решения

Проверены доступ к PostgreSQL, обслуживание динамики и статики,
взаимное чтение файлов GFS2, отключение каждого фронта и backend,
разделение сети backend и восстановление узлов.
